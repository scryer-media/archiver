# Browser verification

Run the development server on port 4173, then open `/tests/browser.html` in a browser. The page exercises the same worker clients used by the app and reports each result. For automated collection, launch an isolated Chromium browser with `--headless --remote-debugging-port=9223` and run `node tests/run-browser.mjs`. The runner uses Node built-ins only and closes its own test tab.

Additional pages use the same runner with a URL argument: `/tests/extended.html` covers native codecs, filters, RAR compatibility and FFT-only parity; `/tests/streams.html` covers standalone streams and compressed TAR; `/tests/tar.html` covers GNU/PAX interoperability and malformed input; `/tests/storage.html` covers lease ownership and failure cleanup. Set `VERIFY_EXPORT_DIR` to a temporary directory to save small generated outputs for independent CLI checks; the runner disposes test storage after export.

`python3 tests/generate-large.py` creates a new temporary fixture directory containing a 300 MiB deterministic high-entropy original, a damaged copy and independent PAR2 recovery. It refuses an existing target directory. `node tests/run-large.mjs` drives real disk-file PAR2/PAR3 FFT repairs, chunk SHA-256 comparison and cancellation cleanup. Use `/tests/large.html?formats=zstd` as the runner URL for the standalone streaming case. Both repairs and the large Zstandard roundtrip passed with a 64 MiB WASM memory allocation; output and scratch bytes stayed disk-backed.

`tests/run-ui.mjs` exercises the production preview using prepared UI fixtures: two dark navigation tabs, ordinary compressed-TAR listing/extraction, contextual parity repair followed by opening the repaired archive, preservation of the selected disk file, and mobile width. Production offline/update checks use the browser debugging protocol to disable networking and observe actual controlling/waiting service workers.

Fixture generators use installed command-line codecs and read-only sibling source fixtures. `generate-compatibility.py`, `generate-streams.py` and `generate-tar-compatibility.py` reproduce the small fixture sets. PAR3 FFT/GF16/interleaved carriers are copied unchanged from the sibling advanced reference corpus generated by official par3cmdline commit `2971702e501f1350b1c7b9d11369af9157d6ed56`; only original data copies are damaged by tests.

Coverage includes archive roundtrips, AES passwords, solid encrypted 7z, corruption, traversal, cancellation, retained output snapshots, and byte-exact PAR2 / RAR recovery-record / REV recovery. Tests do not contact external services.

The optional `/tests/large.html` harness accepts a real disk file and runs TAR, ZIP and 7z creation/extraction. It compares SHA-256 for every 1 MiB input/output chunk, keeping verification buffers bounded. A 300 MiB sparse input with start/end markers passed all three formats; this exercises large input and TAR output streaming, while compressed ZIP/7z outputs remain small.

ZIP, TAR, GZIP and PAR2 inputs were generated locally from the 29-byte verification text. RAR inputs were copied unchanged from the sibling rarpar test corpus (generated RAR5 fixtures). The encrypted 7z input comes from the sibling sevenz-turbo test resources. Passwords are fixture credentials only. These tiny fixtures exercise functionality; they do not constitute a large-file performance benchmark.

`tests/run-review-ui.mjs` extends the production UI checks with repaired-selection replacement and exact extracted bytes, existing-file PAR2/PAR3 creation, same-job 7z plus parity creation and extraction, invalid numeric controls, empty-directory selection, folder saving and collision refusal. Supply the isolated browser debugging URL, production app URL and prepared fixture directory as positional arguments. Folder picker tests supply real OPFS directory handles to avoid native-dialog automation; this proves the browser API path, not host filesystem permissions. The harness snapshots only its tiny test downloads before clearing temporary app output.

`/tests/review-native.html` adds multipart 7z, directory-only and nested-empty-folder archives, mixed healthy/damaged PAR3 publication, unknown-format rejection and encrypted BCJ2 validation. `/tests/review-browser.html` covers adversarial browser storage and ZIP/TAR behavior. Run these with the standard browser runner against the development server so test sources are available. Test-only source pages are not shipped in production.

Progress verification uses three complementary checks. `node tests/progress-model.mjs` (a Node version with native TypeScript stripping) checks measured rate/ETA math, stale counters, phase boundaries and retries without a browser. `node tests/run-progress-ui.mjs <debug-url> <app-url>` supplies explicit test-only worker telemetry to check percentage, stable ETA, finalization, throttled announcements, mobile layout, cancellation and retry state. It bypasses service-worker/browser caches for that test page without clearing origin storage. `node tests/run-real-progress-ui.mjs <debug-url> <app-url>` runs an actual local 32 MiB incompressible native 7z creation and byte-exact SHA-256 roundtrip, recording the UI's measured byte counts. Use a dedicated test browser/profile and separate preview origin; never point these at an active user job.

To validate changes while another production build is in use, build with `npx vite build --outDir dist-progress`, then `node scripts/build-offline.mjs dist-progress`, and serve that output on a separate port. These commands leave the regular `dist/` build intact. Progress percentages and ETAs describe the measured phase only. Unknown totals, compute-only phases and browser disk finalization remain indeterminate; clock ticks update elapsed/staleness but never invent completed bytes.

## Current creation battery

The current creation matrix excludes PAR3 creation and 7z plus PAR3. Existing PAR3 listing, verification and repair remain available. Earlier PAR3 creation results above describe historical validation; those creation cases are not part of the current supported workflow. RAR creation and split-archive creation are not offered.

`node tests/run-creation-battery.mjs --plan` prints the matrix without browser execution. It contains 49 positive app-API cases, 12 invalid-option cases and 11 production-UI cases. UI cases include streamed GZIP, BZip2, XZ, Zstandard and multi-file TAR, alongside ZIP/AES ZIP, 7z, TAR.XZ, PAR2 and 7z plus PAR2. API combinations cover nine 7z codecs, ten LZMA2 filters, nine standalone streams, nine compressed TAR variants and real automatic ZIP64 creation from 65,536 one-byte entries. The matrix does not claim every Cartesian combination.

Use Node.js 22.18 or newer and a dedicated Chromium debugging endpoint with no active user jobs. Start development and production-preview servers from this checkout, with its matching generated native runtime. Supply a writable local fixture directory containing the documented `streams/manifest.json` (plain ZIP and LZMA2 7z inputs) and `basic-manifest.json` (stored RAR input). Inputs are independently SHA-256 checked; only the three small referenced archives are needed. New seeds, artifacts, downloads and extracted outputs stay beneath the supplied fixture root.

```sh
node tests/check-browser-session.mjs <debug-url> <dev-url>
node tests/run-creation-battery.mjs --execute --confirm-browser-idle --battery-root <local-fixture-root> --endpoint <debug-url> --dev-url <dev-url> --production-url <preview-url>
python3 tests/verify-creation.py --battery-root <local-fixture-root> --evidence <run-evidence.json> --output-dir <new-oracle-directory>
```

The browser asks for the exact fixture directory on each origin. Multi-file UI cases traverse a real, already-granted descendant directory through the app's normal folder-selection handler; the picker-return test seam is explicitly recorded. Streamed UI cases require an actual browser download-completed event and saved-file readback. Staged UI output is exported through the app's download controls, with its original File objects retained until exports finish.

Every successful archive is checked for all expected paths, directories, byte counts and payload hashes. Created PAR2 sets additionally verify, repair a deliberately damaged protected archive and reject insufficient recovery, then re-extract the nested original payload. Independent installed CLI tools validate created artifacts separately; unavailable decoders are recorded rather than treated as interoperability passes. The many-entry ZIP64 test performs app creation/listing and bounded cached-small-archive library reads of every entry, without creating 65,536 host files.

Reports persist per case and collect ordinary failures without stopping the matrix. A browser disconnection or bounded RPC timeout stops that page rather than leaving a hidden job running. `--only-case <comma-separated-ids>` supports a narrow smoke run; unknown IDs are rejected. `--resume-evidence <prior-evidence.json>` reuses only structurally validated successful records with explicit provenance. A report that lacks created artifacts or completed validation cannot count as a pass.

## Password and creation settings controls

`node tests/password.mjs` checks the 24-character browser-CSPRNG generator, unambiguous alphabet, at least 128 theoretical bits, rejection sampling and entropy failure. `node tests/run-password-ui.mjs --execute --endpoint <debug-url> --app-url <dev-url> --output-dir <new-local-directory>` checks actual Generate/Show/Copy controls, a page-scoped clipboard stub, failure feedback, busy disabling and a small encrypted ZIP creation. Generated passwords are neither logged nor written to evidence; screenshots remain masked.

`node tests/run-create-settings-ui.mjs --execute --endpoint <debug-url> --app-url <dev-url> --output-dir <new-local-directory>` checks Simple/Advanced state, detected-type recommendations, preserved format-specific overrides, header-encryption policy and mobile layout. This focused harness captures the actual UI's creation request with a page-scoped engine method replacement; it does not claim codec execution. The creation battery and mixed-plan backend tests separately verify real outputs. Advanced settings render at most 50 files per page and support filename search. Skipped inspection uses conservative general defaults.

## Native folder-picker preflight

Before a large direct-folder run, verify the specifically recorded test browser's live CDP endpoint and use native automation to read its window's accessibility tree. A responsive CDP target alone does not prove that the native picker can be controlled. Keep the test browser separate from user browsers and confirm no owned extraction job is active before any session repair.

If native binding returns `cgWindowNotFound`, preserve the blocked report and do not keep retrying expired picker targets. Bringing forward or repositioning the window may be insufficient. Recreate only the recorded, idle test-browser session using its existing executable/profile, then verify native binding again before launching the test. This recovered the observed session; the underlying cause was not established. Do not reset unrelated browser state, use fake directory handles or bypass the permission prompt.

`node tests/run-large-zip-extract.mjs --execute --confirm-browser-idle --endpoint <debug-url> --app-url <dev-url> --archive <existing-zip> --expected <expected-files.json> --output-root <new-approved-output-directory>` uses a genuine picker and exact-directory marker. The existing two-member 5 GB fixture passed this path after native automation recovered: every output path, byte count and full SHA-256 matched, and the input archive's full hash remained unchanged. Extraction timing excludes picker wait and independent host hashing. This fixture validates both files; it does not add general empty-directory coverage.

## Sparse files, link copies and metadata

Run the actual native-library TAR gate and ZIP worker link-policy regressions after building the current engine runtime:

    node tests/tar-completeness.mjs
    node tests/tar-stream.mjs

The TAR suite executes the application’s Emscripten C ABI, while ZIP cases use the actual ZIP worker under Node. They are separate from browser download tests. Sparse GNU old-format and PAX 0.0/0.1/1.0 fixtures are independently decoded with Python’s standard-library TAR reader. Adversarial targets, canonical aliases, malformed maps, packed-byte mismatches and metadata budgets must reject before member output. Safe-copy mode produces ordinary file bytes only. Existing Python GNU/PAX compatibility fixtures run against the same native library; the former custom parser is no longer shipped.

The stream command runs the native Rust adapter regression: a virtual 100 GiB hole emits 64 KiB zero chunks and stops when the output sink cancels. It does not allocate or benchmark a 100 GB output. Additional native tests cover offsets beyond 4 GiB, aborting an unwritten 9 GiB member, and independent Python decoding of UTF-8 names and timestamp boundaries. Physical sparse-file allocation is not promised.

The small real-browser worker suite requires the current source development server:

    node tests/run-completeness.mjs --execute --endpoint <debug-url> --app-url <dev-url> --output-dir <new-local-directory>

It uses only tiny OPFS fixtures; no native folder grant is requested. Node and browser evidence remain separate. Metadata is returned descriptively and can be downloaded explicitly; browsers cannot apply host ownership or permissions.

Selected-folder compressed TAR routing has a focused regression:

    node tests/compressed-tar-destination.mjs

It checks actual public orchestration and the real TAR worker with mock directory handles and a Node GZIP decoder shim. It proves direct safe-copy mode does not invoke private OPFS predecode, writes through the chosen scratch/member handles, validates unsafe graphs before member writers and removes owned jobs on failure/cancellation. It is not native codec or genuine host-picker proof. Temporary selected-destination space must fit the decompressed TAR plus extracted outputs until scratch cleanup completes.

## Write-budget checks

`node tests/output-budget.mjs` checks finite defaults, explicit 100 GB allowance and logical write/growth accounting. `node tests/output-budget-worker.mjs` drives the actual fallback worker with cumulative ZIP output and unknown expanded stream sizes. Both run in `npm run check`. With the built public native runtime present, `node tests/output-budget-native.mjs` exercises real Emscripten descriptor truncation and writable-map refusal without creating host files. These bounded checks do not rerun large archive benchmarks.
