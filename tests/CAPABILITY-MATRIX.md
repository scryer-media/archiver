# Capability verification matrix

This inventory distinguishes actual archive/parity functionality from optional acceleration backends. A browser smoke test is evidence for its listed case, not every combination of codec, filter, encryption, layout and volume size. Runtime GPU/SIMD/CPU dispatch and threaded parallel execution are performance choices; this browser engine runs synchronous work in a worker and does not claim native parallel-backend parity.

Deflate64, LZS and Lizard appear as method identifiers in sevenz-turbo but lack actual encoder/decoder dispatch; they are not supported codecs to enable. PAR3 sparse matrices, high-rate FFT, parent-set backups, nested protection and automatic source-directory inference are explicitly unsupported by the crate. No browser support is claimed for them.

The installed 7zz oracle lists RAR headers but its build does not decode RAR compression. RAR checks therefore use sibling original payload bytes when available, and independently listed header CRC32/size otherwise. This limit is recorded rather than silently treating the app engine as an independent oracle.

## Streamed-download integration evidence

Actual isolated production UI tests covered ZIP and AES ZIP create/extract, correct/wrong passwords, native GZIP/RAR/7z extraction, unsupported output rejection, cancellation and mobile width. Seven additional browser checks passed: ZIP and RAR end-CRC failures each transferred the full 6 MiB before the browser interrupted the download; withheld EOF followed by integrity abort never completed; owner cancellation interrupted; a transfer survived 45 seconds before its first byte and 45 seconds between chunks with exact SHA-256; offline current-build reload and GZIP download completed with exact bytes. Dedicated-worker transport checks are distinguished from app UI checks in the test evidence.

A real local SSD stored RAR streamed 5,000,000,000 bytes, independently size/SHA-256 verified, in about 9 seconds. Native heap was 64 MiB; sampled aggregate browser RSS peaked near 3.09 GiB, which includes shared pages and is not a whole-browser bounded-memory guarantee. The real 100 GB Media attempt failed data CRC at finalization. A subsequent complete independent source-payload scan found one bad 8 MiB fixture chunk; source CRC32 7556f423 exactly matched the browser error. The bad chunk was backed up, deterministically corrected and reopened/verified (repair-proof-finalized.json). The failed extracted output had been removed and was not fully hashed. The corrected stream subsequently stopped after approximately 315 seconds and 12.8 GB with a browser cancellation; the reviewed service-worker lifetime fix subsequently passed a 395-second paced browser download with exact saved-byte/SHA verification. The next corrected-input attempt crashed near 85.6 GB; final browser completion and saved-output verification remain unproven. Virtual 100 GiB offset tests and this failed run must not be reported as a successful 100 GB extraction.

Healthy RAR recovery-record/REV verification passes native tests and the actual app API battery. The independent Media battery passed 96 aggregate checks: 67 catalog cases plus 11 negative controls, 15 creation roundtrips and three production UI flows. Successful earlier checks retain provenance; the affected Unicode-path, numeric-rejection and PAR2 publication cases were rerun, then the final production UI cases passed. All 83 physical input hashes remained unchanged. The 65,536-entry ZIP64 case validates actual app listing plus sequential full payload hashes for every one-byte entry, without 65,536 host output files. All nine 7z codec roundtrips passed at that historical checkpoint; its three installed-decoder gaps were subsequently closed by the independent supplemental run recorded below. The separate actual large ZIP64 run passed: app streamed creation from 5,000,000,000-byte and 44-byte inputs, independent full CRC32/SHA-256 verification, actual app extraction into a genuinely granted local folder and full saved-file SHA-256. Central-directory and second-member header offsets both exceeded 4 GiB.

The final service-worker update gate passed six actual browser checks with the real generated worker, including Origin/Vary matching, integrity-failure preservation, waiting updates, previous-cohort hashed imports, bounded two-cohort retention and offline loading with HTTP cache disabled. Production offline HTML/JS/CSS also came from Cache Storage. Save all canonical filename aliases now reject before any filesystem mutation; six component cases assert zero file/folder/writer creation for collisions.
